The problem

Three places an agent can run code. Two of them can hurt you.

Coding agents now install packages, execute generated scripts, and call tools on their own. Where that runs decides what a bad command — or a prompt injection — can reach.

On the host

Full blast radius

The command runs as you. It can read ~/.aws, your SSH keys, your browser cookies, and everything you can rm. One bad tool call is a bad day.

In a container

One shared kernel

Namespaces are a packaging boundary, not a security one for hostile code. Container escapes are a recurring class of CVE, and a leaked host mount or socket undoes the rest.

In someone's cloud

Your code leaves the building

Third-party sandboxes mean your source, your data, and your prompts travel to infrastructure you don't control — plus latency, plus a bill, plus a new place to be breached.

How Moat is different

One shared kernel is one too many.

Moat runs each task in a real virtual machine on KVM — the same isolation model AWS uses to keep Lambda and Fargate tenants apart — started by a seccomp-jailed Firecracker process. The guest gets its own kernel and a disposable disk. Nothing of yours is inside it.

What "isolated" actually means here

Seven guarantees, enforced by the platform.

01

Hardware isolation

Firecracker + KVM, a separate guest kernel per task. Not namespaces.

02

Ephemeral by default

One microVM per task, never reused, destroyed on exit, TTL, or idle.

03

Nothing leaks in

Host environment is deny-by-default. Every file, env var, and stdin is scanned for secrets and blocked.

04

Nothing leaks out

Per-VM network namespace with no route to the host, cloud metadata, or your LAN.

05

Filtered egress

Outbound traffic goes only through a domain-allowlisted proxy, transparently redirected so the guest can't opt out.

06

Contained blast

cgroup v2 CPU, memory, and PID caps plus Firecracker I/O rate limiters on the VMM process.

07

Runs on your metal

Your workstation or your server. Nothing is ever sent anywhere. Install with one command.

The loop

Create, use, destroy. Then do it again from scratch.

The agent never accumulates state. Every task starts in a clean box and ends with the box gone. From a warm pool, a fresh sandbox is ready in about a millisecond.

1

Ask for a sandbox

moat_create { "template": "python", "ttl": "10m", "network": "deny" }
→ { "id": "mb-7f3a19c4", "expires_at": "2026-08-30T18:40Z" }
2

Put files in — they get scanned

moat_write_file { "id": "mb-7f3a19c4", "path": "/work/task.py", "content": "..." }
→ { "bytes": 412, "sha256": "9f2c..." }
→ 409 secret_detected: "AWS_SECRET_ACCESS_KEY" at line 4 — blocked
3

Run commands, stream the output

moat_exec { "id": "mb-7f3a19c4", "argv": ["python","/work/task.py"], "timeout": "60s" }
→ stdout/stderr streamed … { "exit": 0, "timed_out": false }
4

Pull results out

moat_read_file { "id": "mb-7f3a19c4", "path": "/work/out.json" }
→ raw bytes + sha256
5

Destroy it

moat_destroy { "id": "mb-7f3a19c4" }
→ VM stopped, disk discarded, 0 bytes persisted  (also automatic on TTL / idle)

Built for agents, not humans

Point your agent at Moat with one config block.

Moat ships an MCP server and a SKILL.md that teaches an agent the whole ephemeral workflow — when to sandbox, how to read results, and never to hand over the user's real credentials.

~/.config/agent/mcp.json
{
  "mcpServers": {
    "moat": {
      "command": "moat-mcp",
      "args": ["--socket", "/run/moat/moatd.sock"]
    }
  }
}
MCP tools

Seven verbs

moat_create, moat_exec, moat_write_file, moat_read_file, moat_get, moat_list, moat_destroy. Streamed exec output, exit codes, timeouts, and secret-block errors are all first-class results.

SKILL.md

The playbook, in the repo

Describes the create→put→exec→get→destroy loop, when a command belongs in a sandbox, how to surface a blocked secret to the user instead of overriding it, and defaulting to network: deny.

Works with any MCP client — Claude Code, Claude Desktop, Cursor, Continue — plus a plain HTTP/JSON API and the moat CLI.

Threat model

Every way a command tries to reach you — and what stops it.

If the command tries to…Moat's control
Read or write host filesNo host filesystem is mounted. The guest sees only a shared read-only rootfs and its own ephemeral copy-on-write scratch disk.
Steal host credentialsThe host environment is deny-by-default. Every variable, file, and stdin crossing into a sandbox is scanned for keys, tokens, and private material, and blocked unless explicitly allowed and audited.
Pivot to your LAN or cloud metadataEach VM gets its own network namespace. nftables drops traffic to the host, to 169.254.169.254, and to RFC‑1918 ranges.
Exfiltrate data over the networkEgress is allowed only through a domain-filtered forward proxy, transparently redirected at the firewall so a client that ignores HTTP_PROXY still cannot bypass the policy.
Fork-bomb, exhaust memory, or thrash diskcgroup v2 cpu.max / memory.max / pids.max on the VMM, plus Firecracker token-bucket rate limiters on the disk and NIC.
Exploit a container-escape-class kernel bugThere is no shared kernel. The guest runs its own kernel under KVM, launched by a Firecracker process under a seccomp filter with dropped privileges.
Leave state behind for the next taskOne microVM per task, never reused. Stopped and discarded on exit, TTL, or idle timeout. An orphan reaper cleans up anything a crash leaves running.

Install on your own Linux box

One command. No account. Nothing phones home.

$ curl -fsSL https://moat.sh/install | sh
Prerequisites

A Linux host with KVM

x86_64, /dev/kvm present, and systemd (or run with --rootless using a delegated cgroup slice). Bare metal, or a VM with nested virtualization.

What the installer does

Checks, fetches, verifies

Confirms virtualization support, installs moatd, moat, and moat-mcp, downloads a cosign-verified kernel and base rootfs, writes /etc/moat/moat.toml, and installs a systemd unit.

verify
moat doctor                       # KVM, cgroup delegation, image signatures
moat run -- echo hello from a microVM
moat uninstall                    # binaries, images, unit, config — all of it

FAQ

The questions everyone asks first.

Isn't this just Docker?

Containers share the host kernel, so a container escape — a real, recurring class of CVE — puts the attacker on your box. Moat gives each task its own kernel under KVM: the same isolation model AWS uses to keep Lambda tenants apart.

Do I need root?

The daemon needs access to /dev/kvm and can run inside a delegated systemd cgroup slice without full root. The installer sets this up. A rootless mode using user namespaces is supported for the network-isolated path.

Does my code or data leave my machine?

No. Moat runs entirely on your host. Nothing is sent anywhere. The filtered egress proxy is the only outbound path, and you set its allowlist.

Which agents work with it?

Anything that speaks MCP — Claude Code, Claude Desktop, Cursor, Continue, and others — plus a plain HTTP/JSON API and the moat CLI for everything else.

What's the overhead?

A microVM adds a few MiB of memory and single-digit-millisecond start latency from a warm pool. Cold boot to a ready agent is about 24 ms.

GPU workloads?

Not yet. Firecracker has no device passthrough. GPU support is on the roadmap via an alternative VMM backend.

macOS or Windows?

The host must be Linux with KVM. On macOS, run Moat inside a Linux VM. On Windows, WSL2 with nested virtualization works.
