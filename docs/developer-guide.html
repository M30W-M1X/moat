One microVM per task. Never reused. Burned when the task ends.

Moat is a Go control plane that starts, isolates, and reaps Firecracker microVMs as disposable, hardware-isolated sandboxes. This guide works from the isolation boundary outward: first the mechanism, then each package, then the supply chain, the build, the API, and how to run moatd in your own environment.

module: github.com/M30W-M1X/moat go 1.27.0 kernel: vmlinux 6.1.182 (pinned) base: alpine@sha256:c64c687c…

01Architecture at a glance

A single daemon, moatd, owns the control plane: authentication, concurrency quotas, templates, a TTL janitor, Prometheus metrics, and structured request logs. Everything that touches an untrusted workload lives behind it — the warm pool, the Firecracker driver, the egress proxy — and each running sandbox is one microVM with its own kernel, network namespace, and cgroup.

The lifecycle of one request

A create then exec then destroy moves through the daemon, the boot path, the network setup, and the guest agent. The audit log records each boundary crossing.

03The security model

Moat runs code it does not trust. The isolation is layered so a break in one layer still meets another. Read the diagram from the untrusted centre outward.

Threat model

  • Trusted: the host kernel, KVM, Firecracker and the jailer, moatd, the guest agent binary, the pinned kernel and base image.
  • Untrusted: every process the guest runs, every byte it writes, every packet it sends, and every file a caller asks to put into a sandbox.
  • Out of scope: a KVM or hardware (microcode, speculative execution) vulnerability, a malicious host operator, GPU workloads (Firecracker has no VFIO — DD-11).
Known gap · G-19 The cold-boot rootfs is read-write. vm.Boot attaches the root drive with IsReadOnly: false, and coldBoot points the machine straight at the template rootfs.ext4. Only the warm pool copies the rootfs per member, so a non-pooled sandbox writes into the shared template image for the life of that boot. The fix — attach the root drive read-only, or copy per sandbox — is a planned VM-driver change.
Also The jailer path (-jail) and real-uplink NAT need a root host. UFFD restore needs read access to /dev/userfaultfd or vm.unprivileged_userfaultfd=1 (G-14).

04Firecracker driver — internal/vm

Boot(ctx, m config.Machine, log) (*Instance, error) builds a firecracker.Config — one root drive, one vsock device, and a network interface when m.Net is set — then startMachine applies either the jailer (cfg.JailerCfg) or a plain unprivileged process, starts the VMM, and waits for the guest agent on vsock. Instance holds the VMM pid so internal/cgroup can cap it.

Cold boot versus snapshot restore

Gotcha · G-12 PauseVM/ResumeVM on the same VMM process breaks the guest vsock on this Firecracker build. The warm pool keeps members running, not paused. Snapshot restore starts a fresh process and is unaffected.

05The guest agent & vsock

The agent is a static (CGO_ENABLED=0) binary. The kernel runs it as PID 1 through init=/sbin/guest-agent. As PID 1 it must never return — the kernel panics if init exits — so every fatal path calls haltForever. On start it mounts /proc, /sys, /dev (tolerating EBUSY), /dev/pts, /dev/shm, a tmpfs /run; sets a base PATH and /etc/resolv.conf; installs a SIGCHLD reaper; and serves gRPC on AF_VSOCK port 5252.

The vsock handshake

Firecracker multiplexes guest vsock connections over one host Unix socket. To open a guest connection the host connects to that socket, writes CONNECT <port>\n, reads OK <hostport>\n, and then the stream is a raw pipe to the guest listener. internal/vsockconn implements it; internal/agentclient wraps it in a gRPC ClientConn with a custom dialer. Host CID is 2. The first guest is CID 3.

RPCShape
Infoagent version, pid, uname -r, uptime — the host's readiness check
Execrequest: argv, env, dir, stdin, timeout_ms, tty+size. Stream: Started{pid}, then stdout/stderr chunks, then one Exit{code, signal, timed_out}. Timeout kills the process group.
WriteFilefirst chunk sets path+mode; every chunk carries data. Response: bytes_written + hex SHA-256.
ReadFiledata chunks, then a final chunk with eof, size, sha256, no data.

Files move only through WriteFile / ReadFile over vsock. There is no shared mount.

06Networking — internal/netconf

Apply Plan / Destroy Plan need CAP_NET_ADMIN and CAP_SYS_ADMIN — real root, or unshare --user --map-root-user --mount --net. A Plan (from BuildPlan(lease, uplink)) describes a named netns, a veth pair, a TAP inside the netns, a static /30 guest address from the 10.62.0.0/16 pool, and the kernel ip= argument so the guest configures the NIC at boot with no DHCP.

chain forward {
  type filter hook forward priority 0; policy accept;
  ct state established,related accept
  ip daddr { <tap /30>, <veth /30> } accept
  ip daddr 169.254.0.0/16 drop        # link-local + cloud metadata
  ip daddr 127.0.0.0/8   drop
  ip daddr 10.0.0.0/8    drop          # RFC-1918
  ip daddr 172.16.0.0/12 drop
  ip daddr 192.168.0.0/16 drop
}

07Resource limits & the warm pool

cgroup.Apply(name, pid, Limits) (remove func(), error) writes cpu.max, memory.max, pids.max into a new leaf under this process's delegated systemd subtree (…/user@<uid>.service/microvm/mvm-<id>). It needs no root when systemd delegation is in effect. Instance.Stop calls the returned remove after the VMM exits. Limits is {CPUCores float64, MemBytes int64, PIDs int64}; a zero field means no cap. Firecracker's own per-VM token-bucket rate limiters cap the rootfs block device and the network interface (one-second refill).

The pool — internal/pool

pool.New(ctx, Options{Size}, base, log) starts Size microVMs from a copy of the base rootfs and keeps them running and idle. Acquire(ctx) returns a *Lease — p50 about 1 ms — carrying a TTL and an idle timeout. Lease.Touch() resets the idle clock; a background sweep force-releases a straggler. Lease.Release() discards the member (one VM per session) and refill starts a replacement. moatd -pool N turns it on; it serves only non-networked sandboxes.

server.New(cfg, log) validates config, builds the template map, runs the image check, builds the secret scanner, registers metrics. Start(ctx) starts the pool, writes daemon.start, starts the TTL janitor. Shutdown(ctx) writes daemon.stop, destroys every sandbox, waits for in-flight teardowns.

09Egress & the ingress secret firewall

Egress proxy — internal/egress

One Proxy serves two listeners. Forward: handles CONNECT (filtered by requested host name, no TLS interception) and absolute-URI HTTP; a networked sandbox gets HTTP(S)_PROXY pointed here. Transparent: takes DNAT-redirected raw connections, recovers the pre-DNAT address with SO_ORIGINAL_DST, reads the host from the request line or the TLS SNI, applies the same policy, and splices.

Policy{Allow, Deny []string}. A host is allowed when it matches no Deny entry and (Allow is empty or it matches an Allow entry). Matching is case-insensitive on the exact name or any parent domain. Each decision is an egress.allow / egress.deny audit event with host, port, method, matched rule, the via listener, and the resolved sandbox and token. Both go on the async audit path so a guest cannot flood the writer with denials.

Secret firewall — internal/secretscan

secretscan.New() loads the vendored Gitleaks rule set (gitleaks.toml, MIT). The Gitleaks module itself is not imported — it pulls 200+ dependencies. A slim in-repo evaluator runs a keyword prefilter, the regex, an optional Shannon-entropy floor, then the allowlists.

moatd scans every -env value, every stdin, and every file body on the way in. A hit returns 409, unless the token has allow_secret_override and the request sets allow_secrets: true (audited), or -secret-redact is on (a marker replaces the secret). secret.block / allow / redact events record only the target, the deduped rule ids, and a count — the matched value never leaves the scanner. A failed secret.allow or secret.redact audit write returns 503: the content does not enter with no durable record.

10The audit log — internal/audit

An append-only JSONL log with a SHA-256 hash chain. Each event's hash is the SHA-256 of its canonical form (keys sorted at every level, hash omitted, ts in RFC3339Nano UTC). Each event's prev is the previous event's hash. The first event's prev is 64 zeros.

11The image pipeline

make images runs four steps: kernel, rootfs, sbom, lock. The result is a byte-identical rootfs.ext4 on one toolchain, a pinned + hash-checked kernel, a CycloneDX SBOM, and images.lock. moatd verifies the kernel and rootfs against the lock at startup and fails closed on a mismatch.

Rootfs determinism controls

Non-determinism sourceControl
the alpine:3.20 tag movespin BASE_IMAGE=…@sha256:c64c687c…

the agent binary embeds paths + a build idgo build -trimpath -buildvcs=false -ldflags='-s -w -buildid=', toolchain go1.27.0

callers disagreed on sizeROOTFS_SIZE frozen at 256M
Scope of the guarantee Byte-identical holds for a fixed toolchain (same podman, e2fsprogs, tar, go). On a different e2fsprogs the package set and the SBOM still match, but the ext4 byte layout can shift. moatd enforces the digest from the lock that shipped with that image, so the runtime check is unaffected.

Bumping the kernel or base image

  1. Resolve the new pin values (commands in the plan).
  2. Edit the constants in build/fetch-kernel.sh, build/build-rootfs.sh, and the Makefile.
  3. make images && make images-verify.
  4. cp build/artifacts/images.lock images.lock and commit.
  5. Re-sign images.lock.sig at release time.

Extra userlands — build/templates/

The default rootfs is the reference image and the only one in images.lock. For a language runtime or a demo shell, add a template: a build/templates/<name>/ directory with a Dockerfile and a template.env. build/build-template.sh runs podman build, then the same rootless export + timestamp-normalise + mkfs.ext4 path as build-rootfs.sh, and writes build/artifacts/<name>-rootfs.ext4.

make template NAME=python        # copy build/templates/_skeleton
make template-image NAME=python  # build build/artifacts/python-rootfs.ext4
make demo-image                  # the dev-shell toolchain image
make minimal-image               # the small test image

Templates are byte-stable within a day only — apk add tracks the live Alpine index — so they are not pinned in images.lock. moatd selects one by the rootfs path in each moatd.json template entry; a client asks for it with {"template":"<name>"}. See build/templates/README.md.

Import an existing image — moat template import

moat template import <ref> (or --from-archive <file>) builds a template rootfs straight from a container image: podman pull / podman load → record the @sha256 digest → read the image config → podman export → inject /sbin/guest-agent → auto-size → mkfs.ext4 -d. The pipeline is internal/imgimport. The image's ENV / WORKDIR / ENTRYPOINT become the template's env / workdir / default_argv, which moatd applies to every exec — a request value always wins. linux/amd64 only. Not in images.lock; the source digest is the record. Without --config the command writes <data>/<name>.template.json and prints the moatd.json snippet.

Template exec defaults. moatd applies a template's env and workdir to every exec in a sandbox from that template, and runs default_argv when a request sends no argv. MCP server & the Go client

moat-mcp is a Model Context Protocol server over stdio exposing moat_create, moat_list, moat_destroy, moat_exec, moat_write_file, moat_read_file. Point it at a running moatd with MOAT_ADDR and MOAT_TOKEN. A secret block comes back as an IsError result that tells the agent to ask the user. internal/moatapi is the Go client — Create, List, Destroy, Exec, PutFile (*SecretBlockedError on 409), GetFile, Audit, Report.

The demo — demo/run.sh

A scripted, self-checking walk-through: it starts moatd with a template store (dev-shell, rhel9, and an imported container), creates sandboxes over the HTTP API, runs a real Go build in one, copies the binary out, runs a RHEL 9 sandbox, and checks each isolation property (own kernel, private rootfs, secret firewall, hash-chained audit, imported-image exec defaults). Needs /dev/kvm, curl, jq, and podman. It exits non-zero on the first failed check. Step table in demo/README.md.

14Deploying moatd

Host requirements

  • Linux / x86-64 with nested or bare-metal KVM. Bare metal for production; GCP nested virtualization works for dev.
  • /dev/kvm accessible to the moatd user.
  • firecracker + jailer on PATH.
  • An uncompressed vmlinux and a rootfs.ext4 — from make images, the release tarball, or install.sh.
  • cgroup v2 with a delegated systemd subtree for rootless resource caps. Without it, the caps need root.
  • For networked sandboxes: nft on PATH and CAP_NET_ADMIN + CAP_SYS_ADMIN.

Run moat doctor on the target host — one line per check.

Installer

curl -fsSL https://raw.githubusercontent.com/M30W-M1X/moat/main/install.sh | sh

Checks Linux / x86-64 / KVM, resolves the latest GitHub release, verifies SHA-256 (and cosign when configured), installs binaries to /usr/local/bin and images + images.lock + sbom.cdx.json to /var/lib/moat, writes a starter moatd.json, installs deploy/moatd.service. Flags: --user --prefix --data --version --no-service --dry-run.

systemd unit

deploy/moatd.service sets DeviceAllow=/dev/kvm rw, NoNewPrivileges, ProtectSystem=strict, ProtectHome=read-only, PrivateTmp, and a read-write path list of /var/lib/moat and /run/moat. For networked sandboxes add AmbientCapabilities=CAP_NET_ADMIN CAP_SYS_ADMIN. Then systemctl enable --now moatd.

Directory resolution

  • data (vmlinux, rootfs.ext4, images.lock, audit): $MOAT_DATA → $XDG_DATA_HOME/moat → ~/.local/share/moat → /var/lib/moat. In a checkout: <repo>/build/artifacts.
  • run (sockets, pid files, scratch): $MOAT_RUN → $XDG_RUNTIME_DIR/moat → /run/moat → a temp dir.
Rootless vs root Rootless covers cold-boot sandboxes, exec, file I/O, resource caps (with delegation), the audit log, the egress proxy in HTTP_PROXY mode, and snapshots. Root or unshare is needed for the network namespace path, the transparent DNAT, the jailer, real-uplink NAT, and UFFD restore without /dev/userfaultfd.

The audit log

moat audit tail -dir /var/lib/moat/audit follows. moat audit query -dir … -since -15m -type exec filters offline. moat audit verify -dir … recomputes the chain and exits non-zero on a break. Over the API, add -addr and -token (the token needs audit_read: "all" for an unfiltered pull).

Crash recovery

moatd runs vm.Reconcile at startup and kills orphan Firecracker processes, one orphan.reap event each. If moatd refuses to start with an audit error, run moat audit verify -dir <dir>, move the named file aside, and restart.

Every footgun that cost real debugging time is a numbered G-N entry in the project "Gotchas" note (G-1 … G-19), in a symptom → cause → fix shape. Read it before a deep change to the kernel args, the image pipeline, the netns path, or the audit writer.

17Limits & roadmap

  • Cold-boot rootfs is read-write (G-19). Fix: attach the root drive read-only, or copy per sandbox.
  • No snapshot-templated warm pool — the pool cold-boots its members.
  • A gRPC northbound surface alongside REST is planned.
  • A template registry (moat template pull python) is a deferred CDN job. moat template import <ref> already covers the common case.
  • CI — the repo has none yet. make images-verify is the exact check a CI job would run.
  • Signing images.lock in an automated release is manual today.
  • GPU workloads are out of scope for Firecracker (DD-11). A parallel gVisor / Cloud Hypervisor backend would keep the VM-driver interface abstract.

Style: all comments and log / error strings follow ASD-STE100. Durable decisions go to the agentcairn vault; full write-ups to ClaudeVault/projects/microvm-controller/; every footgun to the G-N log. Non-trivial work goes through a spec in docs/superpowers/specs/ and a plan in docs/superpowers/plans/ before implementation. No new Go module dependency without a strong reason.
