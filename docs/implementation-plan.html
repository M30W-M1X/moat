A Firecracker control plane for AI agent sandboxes

How to build a Go daemon that boots, isolates, and reaps Firecracker microVMs as disposable, hardware-isolated sandboxes for untrusted AI agent code and tool use.

The bet

Build a custom Go daemon on firecracker-go-sdk, not a container runtime

Every serious AI-sandbox platform — E2B, Fly.io, CodeSandbox — converged on the same shape: a bespoke Go control plane talking to the Firecracker Unix-socket API, snapshot-based instant boot with userfaultfd, a vsock guest agent, and host-enforced network isolation. firecracker-containerd and Kata add an OCI/CRI layer this project does not need and pay for it in cold-start latency and snapshot complexity. Start low-level; you can wrap OCI later if a use case demands it.

  • IsolationFirecracker + Jailer on KVM — one microVM per task, never reused across sessions
  • Control planeGo daemon using firecracker-microvm/firecracker-go-sdk, dropping to the raw socket API for snapshot/UFFD
  • Guest agentStatic Go or Rust binary as PID 1, gRPC over AF_VSOCK (exec, file I/O, health)
  • Boot strategyBuild once → snapshot → restore via UFFD lazy paging; warm pool of paused VMs for <25 ms lease
  • NetworkingPer-VM network namespace + TAP + /30 IPAM; nftables egress filter; outbound proxy for domain allowlisting
  • StorageShared read-only rootfs.ext4 + per-VM ephemeral CoW scratch disk; files move over vsock, never virtio-fs/NFS
  • HostBare metal (Equinix / Hetzner / AWS *.metal) for prod; GCP nested virtualization for dev
  • Not GPUFirecracker has no PCI passthrough. GPU agent workloads need gVisor or Cloud Hypervisor instead.
01

Why Firecracker for this workload

AI agents run model-authored code, shell commands, and network calls — untrusted by definition. The isolation boundary has to be a real one, and it has to open in tens of milliseconds so an agent step does not stall on infrastructure. That combination rules out plain containers (shared kernel) at one end and full QEMU VMs (too slow, too heavy) at the other.

TechnologyBoundaryCold startHost RAM / VMGPUFit
Firecracker pick Hardware (KVM microVM) 5–125 ms

QEMU (microvm) Hardware (KVM) 100–500 ms ~30–80 MB Yes Legacy device compatibility; not worth the overhead here

Firecracker's device model is deliberately tiny — no PCI, no BIOS, no USB, ~50k lines of Rust — which is exactly the property you want facing hostile code. The cost is that it gives you nothing above the VMM: no networking policy, no image management, no scheduler. This project is that missing layer.

02

Control-plane choice

The question is not "which orchestrator" but "how much abstraction to accept over the raw Firecracker socket." More abstraction means faster to a first boot and slower, more constrained forever after.

OptionStatusVerdict for this project
firecracker-go-sdk use Active (AWS + community) Typed Go wrapper over the full REST API, jailer arg construction, process lifecycle, CNI hooks. The right foundation. Drop to the raw socket for snapshot-load + UFFD, which the SDK models only loosely.
firecracker-containerd Active (AWS) Runs containerd + host shim + in-guest agent + runc. Real OCI images, but ~200–400 ms starts and snapshotting fights containerd state. Reconsider only if OCI compatibility becomes a hard requirement.
Kata Containers Active (CNCF graduated) Kubernetes runtimeClass. Firecracker path is deprioritized upstream (no virtio-fs / PCI hotplug); Kata steers users to Cloud Hypervisor. Wrong altitude unless you are running a K8s multi-tenant cluster.
Weave Ignite / Flintlock Ignite archived; Flintlock near-dead Do not use.
libkrun / krunvm Active (Red Hat) Embeddable VMM library, nice for local dev CLIs. Lacks Firecracker's snapshot / rate-limiter / UFFD ecosystem. Not for a multi-tenant server.
Custom, raw socket only You maintain it Maximum control, but you re-implement process supervision, socket pooling, and jailer config generation that the Go SDK already ships. Use the SDK and specialize where needed.

Language: Go for the daemon, Rust optional for the guest agent

Go is the de-facto language for this layer — flyd, E2B's orchestrator, containerd, and Kubernetes are all Go. It gives you vishvananda/netlink and google/nftables for host networking, cheap goroutine concurrency for thousands of Unix sockets, and the only maintained Firecracker SDK. Python is a poor fit for the supervisor (GIL, GC pauses, weak low-level networking). The guest agent is the one place Rust earns its keep: a fully static binary with a <3 MB footprint and no libc surprises as PID 1 — though a static Go binary is a perfectly acceptable v1.

How the leaders build it

The pattern is remarkably consistent across independent teams:

PlatformWhat they do that this plan borrows
E2B closest analog Firecracker on bare-metal GCP/AWS, orchestration in Go (over Nomad). Templates built from Dockerfiles, booted, then captured as a memory + filesystem snapshot; restore uses track_dirty_pages + UFFD lazy paging for <150 ms sandbox start. Guest daemon envd speaks gRPC/ConnectRPC over vsock: process spawn, stdout/stderr streaming, file up/download, Jupyter kernels. Source is open.
Fly.io flyd, a per-host Go daemon on the Firecracker socket. Unpacks OCI layers straight into raw ext4 block devices. Custom minimal Rust init as PID 1 handles signal forwarding, zombie reaping, and splices guest stdout/stderr into vsock. Edge proxy forwards TCP/TLS into the TAP device.
AWS Lambda The original Firecracker workload — microVMs on EC2 metal, trillions of invocations/month. SnapStart pre-initializes the runtime, snapshots encrypted + deduplicated memory, and resumes in <20 ms with lazy hypervisor page faults.
CodeSandbox Clones a running VM in <2 s via memory snapshot + UFFD + copy-on-write disk. Uses virtio-balloon to reclaim RAM from idle sandboxes and overcommit nodes.
Modal counter-example Chose gVisor, not Firecracker, because their workloads are GPU-bound and Firecracker has no VFIO passthrough. The lesson: pick the boundary by whether you need a GPU in the sandbox.
04

Target architecture

One long-running microvm_controller daemon per host. It exposes a northbound API, keeps a warm pool, and owns three subsystem managers that each map to a slice of host state. Everything below the daemon is a Linux primitive — no extra services to run.

05

Engineering decisions

5.1  Guest image pipeline

  • Kernel: uncompressed vmlinux ELF (not bzImage), built from Linux LTS 6.1/6.6 using the Firecracker guest config. Compile in VIRTIO_MMIO, VIRTIO_BLK/NET/VSOCK, EXT4_FS, SERIAL_8250; disable ACPI, PCI, USB, and CONFIG_MODULES. Target <12 MB, ~20 ms boot.
  • Rootfs: author as a normal Dockerfile (python, node, bash, the agent's tools), then docker export the container tarball into a mounted mkfs.ext4 image and inject the guest-agent binary.
# Build rootfs.ext4 from a Docker image
truncate -s 2G rootfs.ext4
mkfs.ext4 -F -b 4096 rootfs.ext4
sudo mount -o loop rootfs.ext4 /mnt/rootfs
cid=$(docker create agent-base:latest)
docker export "$cid" | sudo tar -x -C /mnt/rootfs
docker rm "$cid"
sudo install -m0755 bin/guest-agent /mnt/rootfs/usr/local/bin/guest-agent
sudo umount /mnt/rootfs

5.2  Snapshot & restore — the cold-start answer

  • Boot a template VM once, run setup, then SnapshotCreate → CPU/device state file + guest-memory file.
  • Restore with a userfaultfd handler process: register the memory range, start the guest immediately, and serve 4 KB pages from the snapshot file on fault via UFFDIO_COPY. Start latency becomes independent of guest RAM size — <15 ms.
  • Enable track_dirty_pages for diff snapshots: checkpoint only dirty pages/sectors on pause.
  • On resume, the guest agent must immediately resync the clock (kvmclock / clock_settime) or TLS breaks on skewed certificates.

5.3  Networking & isolation

  • One network namespace per microVM, TAP device inside it, veth pair to the root netns. Kills cross-VM L2/L3 snooping.
  • IPAM: point-to-point /30 or /32 host routes per VM (172.16.X.1 host / 172.16.X.2 guest).
  • nftables in the root netns drops: inter-VM subnet traffic, 169.254.169.254 + link-local (IMDS credential theft), loopback, and RFC-1918 host LAN.
  • Egress proxy for all agent HTTP/S: domain allow/blocklist, per-sandbox rate limits, optional DLP on outbound payloads. This is where agent "internet access" policy actually lives.

5.4  Storage

  • Shared read-only base rootfs.ext4 (is_read_only: true) across hundreds of VMs.
  • Ephemeral CoW scratch disk per VM as /dev/vdb; guest init mounts an overlayfs with scratch as the upper layer. Teardown = unlink.
  • File in/out over vsock only. No NFS, no virtio-fs (Firecracker doesn't support it anyway) — keeps the host filesystem entirely off the guest's attack surface.

5.5  Guest agent

  • Static binary, runs as PID 1 (or an early service), listens on AF_VSOCK (e.g. port 5252).
  • Protobuf RPC: ExecStream (spawn, PTY, live stdout/stderr, exit code) · WriteFile / ReadFile (chunked streams) · HealthCheck heartbeat.
  • Also owns: child reaping, signal forwarding, clean shutdown, post-resume clock resync.

5.6  Lifecycle & warm pool

  • Maintain N pre-booted, paused microVMs. A request leases one, resumes it (<20 ms), and assigns a session ID; the pool asynchronously replaces it.
  • Every lease has a hard TTL and an idle timeout (no vsock activity). Reaping is unconditional: kill the Firecracker PID, delete the netns + TAP, unlink the scratch file.
  • On daemon startup, reconcile: scan running Firecracker PIDs against the lease registry, kill unmanaged ones, flush stray TAPs and /var/run/netns entries.

5.7  Security hardening

LayerMechanism
VMMJailer: unprivileged UID/GID, chroot jail, fresh pid/net/ipc/uts/cgroup/mount namespaces per VM
SyscallsJailer's seccomp-BPF filter restricts Firecracker to ~30 syscalls
Resourcescgroups v2 cpu.max, memory.max (hard OOM boundary), io.max; Firecracker rate limiters on net/disk
Networknftables + netns as above; no host service reachable from any guest
TenancyOne VM per task session, never reused across users/sessions
StorageRead-only base image; every write lands on a scratch disk wiped at teardown

5.8  Host infrastructure

  • Prod: bare metal — Equinix Metal / Hetzner / OVH, or AWS c6i.metal-class. Highest density, no nested-virt jitter.
  • Dev / staging: GCP with --enable-nested-virtualization (n2/c2), or Azure Dv5/Ev5. Standard AWS EC2 does not do nested virt — metal only there.
  • Linux 6.1+ recommended (modern userfaultfd); raise fs.file-max and inotify limits; cap max VMs/host by physical cores.
06

Phased roadmap

Each phase is independently demoable. Snapshotting and the warm pool are deliberately deferred — they are an optimization over a working boot path, not a prerequisite.

Phase1

Minimal viable microVM

  • Kernel + rootfs build pipeline (scripted, reproducible)
  • Go controller launches a jailed Firecracker process via firecracker-go-sdk
  • Vsock echo between host controller and guest

Exit: one command boots a jailed microVM and round-trips a vsock message.

Phase2

Execution & filesystem interface

  • Guest agent: Exec(cmd, env) → stdout/stderr/exit, plus WriteFile / ReadFile
  • Protobuf schema + streaming over vsock; PTY support for interactive commands
  • Host-side client library for agent-framework integration

Exit: run untrusted code in a fresh VM, stream output, pull artifacts out.

Phase3

Network isolation & security

  • Automated netns + TAP + /30 routing in Go (netlink)
  • nftables rules: inter-VM drop, metadata-IP block, egress-only
  • cgroups v2 CPU/memory limits via jailer; Firecracker rate limiters

Exit: a hostile guest cannot reach the host, other VMs, or cloud metadata.

Phase4

Snapshotting & warm pool

  • Snapshot-after-boot; restore with a userfaultfd handler
  • WarmPoolManager maintaining N paused VMs for <25 ms lease acquisition
  • Background reaper: TTL, idle timeout, startup orphan reconciliation

Exit: p50 sandbox acquisition under 50 ms; no leaked VMs after a controller crash.

Phase5

Production API & observability

  • Public gRPC/REST gateway with auth, quotas, multi-template support
  • Prometheus metrics per sandbox (boot latency, vCPU, memory residency, live count); structured logs
  • Egress guardrail proxy: domain filtering, token/secret safety

Exit: an external agent framework drives sandboxes through a documented API under SLOs.

07

Risks & mitigations

RiskSeverityMitigation
Orphaned VMs & leaked TAP/netns after a controller crash high Startup reconciliation pass; treat the lease registry as source of truth; kill anything unmanaged.
Fork bombs / OOM in untrusted guest medium Guest OOM only crashes that microVM. Host cgroups v2 memory.max is the hard backstop; per-VM PID limits in the guest.
Clock skew after restoring an old snapshot breaks TLS medium Guest agent forces clock resync on every resume before releasing the VM to a session.
KVM / fd exhaustion at high density medium Raise fs.file-max and inotify limits; enforce a per-host VM cap derived from physical cores and RAM.
UFFD handler is a new, security-sensitive host process medium Minimal, audited, one handler per VM, no privileges beyond the mapped range; fuzz the page-fault path.
GPU workloads land on the roadmap later low / known Firecracker cannot do it. Plan a parallel gVisor or Cloud Hypervisor path rather than forcing Firecracker.

Open questions to resolve in Phase 1–2

Go vs Rust for the guest agent (v1 can be Go); device-mapper CoW vs in-guest overlayfs for scratch disks; whether to adopt the E2B envd protocol wholesale or define a leaner one; single-host daemon now vs multi-host scheduler boundary later.
